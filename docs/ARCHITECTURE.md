# Архитектура

Проект использует функции, JSON-конфигурацию и файлы на диске. Spark обрабатывает
события, pandas и sklearn работают с меньшими таблицами признаков на абонента.
Streamlit показывает результаты и отправляет последовательные задания worker.

## Последовательность

```text
raw + late_delivery (CDR, tickets)
  → audit → ingest / preprocess → clean Parquet + daily aggregates
  → snapshots (features + labels + temporal split manifest)
  → train → saved Pipeline + metrics → active_model.json
  → freeze at 76 → saved probabilities → evaluate at 91
```

`demo.py` запускает тот же worker, что кнопки интерфейса. Отдельный сервер,
планировщик, база заданий или дополнительные сервисы не нужны.

## Модули

| Модуль в `src/` | Ответственность |
| --- | --- |
| `data.py`, `audit.py` | Разрешённые источники, кодировки, календарь, качество и проверка цели |
| `temporal.py` | Даты replay, границы окон и расписание |
| `preprocess.py`, `ingest.py` | Очистка, дедупликация, версии tickets, Parquet и дневные агрегаты |
| `features.py`, `labels.py`, `snapshots.py` | Исторические признаки, отдельные исходы и сохранение снимков |
| `train.py`, `evaluate.py`, `predict.py` | Pipeline, метрики, выбор версии и загрузка для прогноза |
| `final.py` | Неизменяемые прогнозы и оценка на общей финальной когорте |
| `worker.py`, `demo.py`, `app.py` | Очередь одного задания, сценарий и интерфейс |

## Время и данные

Для снимка D признаки используют дни D−13…D и только записи, доступные к D.
Когорта — абоненты с валидным CDR в этом окне. Цель равна 1 при отсутствии
валидного CDR в дни D+1…D+14, иначе 0. Неполное окно даёт неизвестную метку.
Ключ примера — `(subscriber_key, snapshot_date)`.

Даты источника трактуются как локальное время одного набора без преобразования
часового пояса. Проверяется `ingest_ts`. Время компьютера не определяет replay.
Полнота исходов подтверждается календарём и аудитом доставки; одного отсутствия
активности недостаточно для положительной метки.

| Этап | Часы доставки | Обучающие снимки | Валидация | Окно исходов валидации |
| --- | ---: | --- | ---: | --- |
| 60 | 61 | 14, 21, 28 | 46 | 47–60 |
| 67 | 68 | 14, 21, 28, 35 | 53 | 54–67 |
| 74 | 75 | 14, 21, 28, 35, 42 | 60 | 61–74 |

На дне 76 сохраняются признаки и прогнозы всех завершённых версий, пороги,
активная версия и SHA-256 файлов. На дне доставки 91 раскрываются исходы 77–90.
Новые модели и пороги по финальным исходам не выбираются. Файлы прогнозов
проверяются по контрольным суммам; оценка соединяет их с метками по точному ключу.

Из CSV удаляются повреждённые строки; исходники не меняются. Качество и исключения
учитываются отдельно. В признаки не входят telemetry, reference, текст обращений,
`retention_contact`, будущие закрытия tickets и другие запрещённые поля.
Источники агрегируются до соединения, сохраняется когорта CDR.

## Модели

Каждый этап полностью обучает Logistic Regression и ограниченный XGBoost.
Медианы заполнения пропусков и StandardScaler для Logistic Regression обучаются
только на train. Сохраняется весь sklearn Pipeline, порядок признаков,
конфигурация, границы окон, входные отпечатки, версии пакетов и метрики.
Вероятности после загрузки сверяются с исходными (`rtol=1e-10`, `atol=1e-12`).

Две новые модели и действующая версия сравниваются на одной текущей валидации.
Кандидат заменяет действующую версию только при строго большей average precision
(`pr_auc`); при равенстве остаётся действующая. Порог 0.5 фиксирован.
Log loss, ROC-AUC, precision, recall, F1 и confusion matrix сохраняются отдельно.
Дисбаланс классов делает PR-AUC и recall особенно важными для интерпретации.

## Сохранение и восстановление

Ingest пересчитывает весь доступный префикс данных. Это простой способ учесть
доставленные записи и версии tickets без отдельной системы инкрементальных обновлений.
Отпечаток включает файлы, конфигурацию и код обработки; неизменившийся пакет
переиспользуется. Результаты сначала записываются во временный каталог, затем
публикуются. Неуспешное обучение не меняет активную модель.

`state/ingest.json` указывает готовый пакет; `snapshots.json` — его снимки;
`active_model.json` — модель. `replay.json` меняется после полной подготовки
пакета и снимков. Поэтому ошибка подготовки не продвигает подтверждённые часы.

`state/jobs/active.json` создаётся эксклюзивно: одновременно выполняется одно
задание. Статусы и stdout/stderr сохраняются в JSON и журнале. После остановки
worker задание помечается прерванным, а готовые этапы доступны для повторного запуска.
Worker и demo запускаются внутри контейнера `app`, где приложение проверяет их PID.
Перезапуск контейнера прерывает текущее задание, поэтому его выполняют между заданиями.

Docker содержит Python 3.11, Java 17 и закреплённые зависимости. Spark использует
два потока и heap 2 ГБ. Крупные повторно используемые таблицы сохраняются на диск
(`DISK_ONLY`): проверка полного префикса выявила нехватку heap при хранении в памяти.
Это увеличивает время обработки; число прочитанных CSV не отражает завершение Spark.

Входные каталоги подключены read-only, `data/processed`, `artifacts`, `state` —
на запись. Пересоздание контейнера сохраняет эти каталоги на компьютере.
