# Прогноз неактивности абонентов

Проект в рамках электива "Аналитика Больших Данных": по CDR и обращениям предсказываем отсутствие CDR-активности
в следующие 14 дней у абонентов, активных в предыдущие 14 дней.
Это косвенный показатель оттока **14-day inactivity proxy for churn**.

## Данные и технологии

Набор содержит 90 дней: **01.10.2025–29.12.2025**. Размеры до очистки:

| Источник | Строк CSV | Содержание |
| --- | ---: | --- |
| CDR | 9 540 853 | Звонки, SMS, интернет: время события и доставки, абонент, длительность, трафик, стоимость |
| Tickets | 142 528 | Обращения: создание, закрытие, канал, категория, результат решения |

CSV разбиты по дням; часть разделов находится в `late_delivery`. При подготовке
исключена 1 001 повреждённая строка CDR. Используются 33 числовых признака;
текст обращений, `retention_contact`, telemetry и справочники в модель не входят.

Код написан на **Python 3.11**. Основные технологии:

| Технология | Применение |
| --- | --- |
| PySpark, Java 17, Parquet | Отдельная очистка, агрегации и подготовка снимков |
| pandas, PyArrow | Чтение готовых таблиц признаков для демо |
| scikit-learn, XGBoost, joblib | Обучение моделей, заполнение пропусков, масштабирование и сохранение |
| Streamlit | Браузерный интерфейс |
| Docker, Docker Compose | Запуск приложения и сохранение данных через подключённые каталоги |

Версии зависимостей закреплены в [requirements.txt](requirements.txt).

## Запуск

Нужен запущенный Docker Desktop с Linux containers. Выполнять из корня проекта.

Исходные CSV должны находиться в `data/raw/{cdr,tickets}/dt=YYYY-MM-DD/`
и `data/late_delivery/{cdr,tickets}/dt=YYYY-MM-DD/`. Используются 90 дней:
01.10.2025–29.12.2025, включая разделы из `late_delivery`.

Для демо также нужны готовые Parquet и снимки в `data/processed/` для дней
61, 68, 75, 76 и 91. Они не входят в Git. Приложение использует этот подготовленный
набор; исходные CSV проверяются по контрольным суммам.
Подготовка нового набора выполняется отдельно — см. [архитектуру](docs/ARCHITECTURE.md#подготовка-нового-набора).

```powershell
docker compose build
docker compose up -d app
```

Откройте [localhost:8501](http://localhost:8501). Интерфейс содержит три раздела:
демонстрация, история моделей, прогноз абонента.

## Продолжить сохранённый запуск

После запуска приложения выполните:

```powershell
docker compose exec -T app python -u -m src.demo
```

Команда продолжит с сохраненного этапа: откроет готовые данные, выполнит обучение,
фиксацию прогнозов и финальную оценку. Повторный запуск
продолжает незавершённый сценарий; выполненные обучения не дублируются.
**Если запуск уже завершён, команда сразу вернёт сохранённый результат.**
Для повторного обучения нужен новый запуск по инструкции ниже.
Если нужных данных нет или исходники изменились, демонстрация остановится
с сообщением об ошибке. Автоматическая очистка или пересборка данных не запускается.

## Обучить модели заново

В существующем `config.json` задайте **два новых каталога** (фрагмент конфига):

```json
"state_dir": "state/check_01",
"artifacts_dir": "artifacts/check_01"
```

Затем выполните все три команды:

```powershell
docker compose build
docker compose up -d app
docker compose exec -T app python -u -m src.demo
```

Конфигурация копируется в образ, поэтому после её изменения нужен `build`.
Будут заново обучены две модели в каждом из трёх запусков обучения, затем выполнены
фиксация прогнозов и финальная оценка. Новые версии появятся в «Истории моделей».
Прежние модели и результаты сохранятся; готовые данные в `data/processed` используются повторно.
Для следующего повтора выберите другое имя, например `check_02`, **для обоих каталогов**.
Пути `data_dir`, `processed_dir` и `snapshots_dir` оставьте прежними.

В разделе «Демонстрация» показаны «Обучение 1 из 3», затем 2 и 3.
Для каждого обучения появляется одно актуальное действие: «Открыть данные» →
«Обучить модели». После трёх обучений — «Зафиксировать прогнозы» → «Проверить прогнозы».
Историческая дата данных показана отдельно от номера обучения.

Соответствие внутреннему расписанию (дни считаются от 01.10.2025):

| Шаг в интерфейсе | Конец периода проверки | Данные полностью доступны |
| --- | --- | --- |
| Обучение 1 из 3 | День 60 | 30.11.2025 — день 61 |
| Обучение 2 из 3 | День 67 | 07.12.2025 — день 68 |
| Обучение 3 из 3 | День 74 | 14.12.2025 — день 75 |
| Сохранение прогнозов | Снимок дня 76 | 15.12.2025 |
| Финальная проверка | Исходы дней 77–90 | 30.12.2025 — день 91 |

Дополнительный день нужен для доставки записей по `ingest_ts`.
Числа 60/67/74 в конфиге обозначают конец периода проверки, а не номер обучения.
**CSV за день 91 не нужен.** Обновление страницы не запускает новое задание.
Модели переобучаются на готовых признаках; сохраняются loss, accuracy, PR-AUC и recall.
В интерфейсе показываются выполнение, завершение или ошибка задания.

## Сохранённые результаты

`data/processed/`, `artifacts/` и `state/` подключены с компьютера:
результаты сохраняются при пересоздании контейнера. Исходные CSV подключены только
для чтения; 1 001 повреждённая строка исключается из обработки.

Внутри выбранного `artifacts_dir`: `runs/` и `models/` содержат обучение и модели,
`final_predictions/` — прогнозы дня 76, `final_evaluation/report.md` — итоговую
таблицу, `comparison.json` рядом — все метрики. Статусы заданий находятся в `state_dir/jobs/`.
Первоначальный аудит сохранён в `artifacts/audit/report.md`.

Остановить приложение после завершения задания: `docker compose stop app`.
Снова открыть с сохранёнными результатами: `docker compose up -d app`.

## Проверки

```powershell
docker compose run --rm pipeline -m unittest discover -s tests -v
```

Проверяются временные границы, защита от будущих данных, повторная обработка,
сохранение моделей, очередь заданий, финальные прогнозы и три экрана приложения.

## Код и документация

Простые функции в `src/`: чтение и очистка → Parquet → признаки и метки →
обучение и прогноз → worker и Streamlit. Настройки находятся в `config.json`,
проверки — в `tests/`.

- [Архитектура и временные правила](docs/ARCHITECTURE.md).
- [Переиспользование домашних работ и рефакторинг](docs/REFACTORING.md).
- [Результаты полной демонстрации и ограничения](docs/DEMO_RESULTS.md).

Порог классификации — 0.5; активная модель выбирается по validation PR-AUC
(average precision). Окна валидации меняются, абоненты повторяются между снимками:
график метрик не доказывает постоянного улучшения. Результаты характеризуют
неактивность в этом наборе данных и не подтверждают расторжение договора.
